[[harness-4-memory|4편]]에서 만든 메모리에는 한 가지 한계가 있었다. 모든 기록이 *내 컴퓨터, 내 계정, 내 경로*에만 쌓였다. 내가 어제 푼 에러를 옆자리 동료의 하네스는 모른다. 팀이 같이 쓰려면 기록을 공용 저장소로 올려야 했다.

기능은 멀쩡했다. 문제는 오로지 **위치**였다. 그래서 [[harness-6-codex|6편]]에서 저장 경로를 한 곳으로 모아 둔 게 여기서 빛을 봤다. 그 한 곳에 "사내 공용 저장소에도 올린다"는 통로를 붙이면 됐다.

## 그냥 올리면 안 됐다

기록 파일을 통째로 올리는 건 세 가지가 걸렸다. 무겁고, 매번 전부 다시 보내면 낭비고, 무엇보다 *민감정보가 그대로 올라갈* 위험이 있었다. 그래서 올리기 전에 세 단계를 거치게 했다.

```mermaid
flowchart LR
    F["기록 (.md)"] --> CH["청킹 (조각내기)"]
    CH --> SC["마스킹 (민감정보 가리기)"]
    SC --> DF["증분 (바뀐 것만)"]
    DF --> DB["사내 공용 저장소"]
```

청킹(chunking)은 긴 기록을 검색하기 좋은 작은 조각으로 나누는 일이다. 증분 적재는 매번 전체를 보내지 않고 *새로 추가된 기록만* 올리는 것이고, 중간에 끊겨도 다음에 이어서 올릴 수 있게 했다. 가장 까다로운 건 가운데, 마스킹이었다.

## 민감정보 가리기

기록에는 작업하다 흘린 토큰이나 키가 섞이기 쉽다. 이게 팀 전체에 노출되면 사고다. 그래서 올리기 직전, 명백히 시크릿으로 보이는 패턴을 정규식으로 가렸다.

```js scripts/lib/memory-scrubber.mjs
const SECRET_PATTERNS = [
  // OpenAI류 키: sk- 뒤 20자 이상
  { re: /\bsk-[A-Za-z0-9_-]{20,}\b/g, replace: REDACTED },          // [!code highlight]
  // GitHub 토큰: ghp_/gho_/ghs_ ...
  { re: /\bgh[posur]_[A-Za-z0-9]{20,}\b/g, replace: REDACTED },
  // AWS 액세스 키
  { re: /\bAKIA[0-9A-Z]{16}\b/g, replace: REDACTED },
  // password=... : 키 이름은 남기고 값만 가림
  { re: /\b(password|passwd|pwd)\s*[:=]\s*("[^"]*"|'[^']*'|[^\s,;&]+)/gi,
    replace: (_m, key) => `${key}=${REDACTED}` },
];
```

요령이 하나 있었다. *과하게 가리지 않기*다. 예컨대 `Bearer` 토큰이면 "Bearer"라는 단어는 남기고 뒤 토큰만 가린다. `password=`도 키 이름은 남기고 값만 가린다. 그래야 가린 뒤에도 문맥이 읽힌다. "여기에 비밀번호가 있었다"는 흔적은 남기되 알맹이만 지우는 것이다.

한국 환경에 맞는 패턴도 더했다. 주민등록번호·휴대전화·카드번호처럼 *구조가 뚜렷한* 개인정보는 종류별 라벨로 가렸다.

```js scripts/lib/memory-scrubber.mjs
{ re: /\b\d{6}-[1-4]\d{6}\b/g, replace: "[REDACTED-RRN]" },        // 주민번호
{ re: /\b01[016-9]-?\d{3,4}-?\d{4}\b/g, replace: "[REDACTED-PHONE]" }, // 휴대전화
{ re: /\b\d{4}-\d{4}-\d{4}-\d{4}\b/g, replace: "[REDACTED-CARD]" },   // 카드번호
```

물론 정규식은 *구조적인* 민감정보만 잡는다. "다음 주 화요일에 김 부장과 미팅" 같은 비구조적 정보는 규칙으로 못 잡는다. 그건 코드가 아니라 운영 정책의 영역으로 선을 그었다. 작성자 신원도 클라이언트가 보내지 않고, 서버가 인증된 사용자로 도장 찍게 해 위조 여지를 없앴다.

## 돌아보면

이 회차는 기능보다 *책임*이 무거웠다. 내 PC에만 있던 기록은 새도 나만의 문제지만, 공용으로 올리는 순간 팀 전체의 위험이 된다. 그래서 "올리기 전에 가린다"는 단계를 흐름의 한복판에 박았다. 정규식 마스킹이 만능은 아니라는 한계도 숨기지 않고, 어디까지는 코드가 막고 어디부터는 정책이 막는지 선을 분명히 그은 게 이 회차의 핵심이었다.

그런데 이 통로는 오래가지 못했다. 다음 편에서 이걸 *걷어낸다*. 같은 일을 더 표준적인 방법이 맡게 되면서, 직접 만든 통로가 중복이 됐기 때문이다. 쌓기의 시대가 끝나고, 덜어내기가 시작된다. 🌱
