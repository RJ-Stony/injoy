[[harness-4-memory|하네스의 메모리를 만든 글]]에서 남겨 둔 한계가 하나 있었다. 모든 기록이 내 PC, 내 계정, 내 경로에만 쌓인다는 것이었다. 그렇게 되면 내가 어제 해결한 에러를 옆자리 동료가 똑같이 겪게 되었을 때, 동료는 같은 해결 과정을 처음부터 반복해야 한다. 이 기록을 함께 사용하려면, 메모리를 사내 공용 저장소에 적재해야 했다.

메모리의 기능 자체에는 문제가 없었다. 문제는 오로지 **기록이 쌓이는 위치**였다. 그래서 [[harness-6-codex|지난 글]]에서 저장 경로를 한 곳으로 모아 둔 것이 여기서 도움이 되었다. 그 한 곳에서 파생되던 `memory/`를, 사내 공용 저장소에도 적재하는 파이프라인에 그대로 연결하면 되었기 때문이다.

## 그대로 적재할 수 없었던 이유

그런데 메모리 파일을 통째로 적재하기에는 세 가지 문제가 있었다. 파일 단위로는 검색하기가 어렵고, 매번 전체를 다시 보내면 낭비가 되며, 무엇보다 **민감정보가 그대로 적재될 위험**이 있었다. 그래서 기록을 적재하기 전에 세 단계를 거치도록 했다.

```mermaid
flowchart LR
    F["기록 (.md)"] --> CH["청킹 (조각내기)"]
    CH --> SC["마스킹 (민감정보 가리기)"]
    SC --> DF["증분 (바뀐 것만)"]
    DF --> DB["사내 공용 저장소"]
```

이 가운데 마스킹은 가장 까다로웠기 때문에 뒤에서 따로 다루고, 먼저 청킹과 증분 적재부터 적어 본다.

## 검색하기 좋게 나누는 청킹

첫 번째 단계는 **청킹**(chunking; 긴 글을 검색하기 좋은 작은 조각으로 나누기)이다. 본문을 일정한 길이로 자르는데, 이때 경계에서 문맥이 잘리지 않도록 앞 청크의 끝과 조금 겹쳐서 자르게 했다. 겹쳐서 자르는 이유는 단순하다. 경계에 걸친 문장이 둘로 나뉘게 되면, 검색할 때 두 청크 모두에서 그 문장을 놓치게 되기 때문이다.

```js scripts/lib/memory-chunker.mjs
const CHUNK_SIZE = 500;       // 한 청크 길이
const CHUNK_OVERLAP = 50;     // 다음 청크가 직전 끝에서 겹쳐 시작하는 양 [!code highlight]
const stride = CHUNK_SIZE - CHUNK_OVERLAP;   // 다음 청크의 시작 간격(450자)
// chunk[0]=chars[0..500], chunk[1]=chars[450..950], ... 겹침 덕에 경계 문장이 통째로 살아남는다
```

한 청크의 길이는 500자이고, 다음 청크는 직전 청크의 마지막 50자와 겹쳐서 시작한다. 이렇게 50자를 겹쳐 두면, 경계에 걸친 문장도 적어도 한 청크에는 온전히 들어가게 된다.

## 바뀐 파일만 보내는 증분 적재

청크로 나눈 뒤에는, 그것을 얼마나 자주 그리고 얼마만큼 보낼지를 정해야 했다. 매번 전체를 보내는 것은 낭비였기 때문에, 마지막으로 적재한 시각 이후에 **바뀐 파일만** 적재하는 증분 적재 방식을 선택했다. 파일이 바뀌면 그 파일의 청크만 다시 보내고, 적재가 끝나면 **마커**(marker; 어디까지 올렸는지 적어두는 표시)를 앞으로 옮긴다. 그래서 적재가 중간에 끊기더라도 다음에 이어서 진행할 수 있다.

```js scripts/memory-sync.mjs
// 한 파일이 마커 이후 변경되면 그 파일의 모든 청크를 포함한다(안 바뀐 청크는 안 보냄)
const changed = allChunks.filter((chunk) => (chunk.mtime ?? 0) > lastMs);  // [!code highlight]
```

적재하는 시점은 사람이 신경 쓰지 않아도 되도록 했다. 세션을 시작할 때 실행되는 트리거가 마지막 동기화로부터 24시간이 지났는지만 확인하고, 지났다면 그때 한 번 적재한다. 여기서도 불변식은 이전과 같았다. 어떤 실패가 발생하더라도 예외를 던지지 않고, 로그만 남긴 뒤 항상 정상 종료하도록 했다. 동기화가 실패했다는 이유로 사용자의 작업이 막혀서는 안 되기 때문이다.

```js scripts/memory-sync-trigger.mjs
const DAY_MS = 24 * 60 * 60 * 1000;
// 24h 경과 시에만 동기화 안내를 내보내고, 미경과면 빈 출력. 실패해도 throw 금지·항상 exit 0. [!code highlight]
```

## 적재하지 않을 기록을 고르는 방법

반대로 적재하지 말아야 하는 기록도 있다. 개인 프로젝트나 민감한 작업의 기록은 공용 저장소에 아예 전달되지 않도록 제외해야 한다. 그런데 이렇게 제외하는 일을 비개발 직군도 코드 없이 말로 할 수 있어야 했다. 그래서 제외 목록을 코드로 관리하지 않고, 주석이 달린 텍스트 파일 하나로 관리하게 했다.

```text memory-sync-exclude.txt
# 이 파일에 프로젝트 폴더 이름(일부)을 한 줄씩 적으면 그 작업 기록은 사내 DB에 올라가지 않아요.
# '#'로 시작하는 줄은 설명이라 무시돼요.
my-personal-blog        # 대소문자 무시 부분문자열 매칭
```

이 파일에 프로젝트 디렉토리 이름의 일부만 한 줄씩 적어 두면, 그 프로젝트의 작업 기록은 적재 대상에서 제외된다.

## 민감정보 마스킹

제외 목록은 프로젝트 단위로만 걸러 낸다. 그런데 적재되는 기록 안에도 작업하다가 남은 토큰이나 키가 섞여 있기 쉽고, 이것이 사내에 노출되면 사고가 된다. 그래서 세 단계 가운데 가장 까다로웠던 것이 마스킹이었다. 적재하기 직전에, 명백히 시크릿으로 보이는 패턴을 정규식으로 찾아서 마스킹하도록 했다.

```js scripts/lib/memory-scrubber.mjs
const REDACTED = "[REDACTED]";
const SECRET_PATTERNS = [
  { re: /\bsk-[A-Za-z0-9_-]{20,}\b/g, replace: REDACTED },              // OpenAI류 키
  { re: /\bgh[posur]_[A-Za-z0-9]{20,}\b/g, replace: REDACTED },         // GitHub 토큰
  { re: /\bxox[baprs]-[A-Za-z0-9-]{10,}\b/g, replace: REDACTED },       // Slack 토큰
  { re: /\bAKIA[0-9A-Z]{16}\b/g, replace: REDACTED },                   // AWS 액세스 키
  // Bearer 토큰: "Bearer "는 보존, 뒤 토큰만 가린다
  { re: /\bBearer\s+[A-Za-z0-9._\-+/=]{8,}/g, replace: () => `Bearer ${REDACTED}` },  // [!code highlight]
  // password=... : 키 이름은 남기고 값만 가린다
  { re: /\b(password|passwd|pwd)\s*[:=]\s*("[^"]*"|'[^']*'|[^\s,;&]+)/gi,
    replace: (_m, key) => `${key}=${REDACTED}` },
];
```

여기서 신경 쓴 것은 **과하게 마스킹하지 않는 것**이었다. `Bearer` 토큰이라면 "Bearer"라는 단어는 남기고 그 뒤의 토큰만 마스킹한다. `password=`도 마찬가지로 키 이름은 남기고 값만 마스킹한다. 그렇게 해야 마스킹한 뒤에도 문맥을 읽을 수 있기 때문이다. 이 자리에 비밀번호가 있었다는 흔적은 남기고, 값만 지우는 것이다.

여기에 한국의 환경에 맞는 패턴도 추가했다. 주민등록번호, 전화번호, 카드번호처럼 구조가 뚜렷한 개인정보는 종류별 라벨로 마스킹하도록 했다.

```js scripts/lib/memory-scrubber.mjs
{ re: /\b\d{6}-[1-4]\d{6}\b/g, replace: "[REDACTED-RRN]" },           // 주민번호
{ re: /\b01[016-9]-?\d{3,4}-?\d{4}\b/g, replace: "[REDACTED-PHONE]" },// 휴대전화
{ re: /\b\d{4}-\d{4}-\d{4}-\d{4}\b/g, replace: "[REDACTED-CARD]" },   // 카드번호
```

물론 정규식으로는 구조적인 민감정보만 찾을 수 있다. "다음 주 화요일에 김 부장과 미팅"처럼 구조가 없는 정보는 규칙으로 찾아낼 수 없다. 그래서 이런 정보는 코드가 아니라 운영 정책에서 다루는 것으로 범위를 나누었다. 기록을 작성한 사람이 누구인지도 클라이언트가 보내지 않고, 서버가 인증된 사용자의 정보로 기록하게 해서 위조할 여지를 없앴다.

## 결론

이번 작업은 기능보다 책임이 더 무거웠다. 내 PC에만 있던 기록은 유출되더라도 나만의 문제이지만, <u>공용 저장소에 적재하는 순간 사내의 위험이 된다.</u> 그래서 적재하기 전에 마스킹하는 단계를 파이프라인에 고정해 두었다. 정규식 마스킹이 만능은 아니라는 한계도 숨기지 않았다. 어디까지는 코드가 막고 어디부터는 정책이 막는지를 분명하게 나눈 것이, 이번 작업에서 중요한 부분이었다.

그런데 이 파이프라인은 오래 유지되지 못했다. 같은 일을 더 표준적인 방법이 맡게 되면서, 직접 만든 부분이 중복되었기 때문이다. [[harness-8-trimming|다음 글]]에서는 이 파이프라인을 제거한다. 계속 추가하기만 하던 작업은 여기까지이고, 이제는 덜어내는 작업이 시작된다. 🍀
