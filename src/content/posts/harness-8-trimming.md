[[harness-1-benchmarking|1편]]부터 [[harness-7-snowflake|7편]]까지는 계속 *쌓는* 이야기였다. 파이프라인을 돌게끔 하고, 도구를 계속 붙이고, 메모리를 공유할 수 있게 했다. 그런데 그사이 모델(**Opus 4.8**)이 부쩍 똑똑해졌다. 오히려 계속 추가만 하던 것에서 *이제는 뭘 빼야 할지 고민하게 되었다.*

기준을 다시 잡았다. "더 똑똑해진 AI가 이 일을 할 수 있나?"가 아니라 **"AI가 이 일을 제멋대로 할 수도 있나?"** 로 봐야 했다.

```mermaid
flowchart TD
    Q{"이 기능의 성격은?"}
    Q -->|"AI가 알아서 잘함<br/>(분류·요약·위임)"| Cut["뺀다"]
    Q -->|"AI가 멋대로 건너뜀<br/>(검증·동의·기록)"| Keep["오히려 강화"]
    Q -->|"특정 트리거로 작동<br/>(특정 시점 자동 실행)"| Same["그대로 둔다"]
```

빼도 되는 건 이미 AI 능력에 흡수되어 있는 부분이었다. 몇 가지가 구체적으로 사라졌다.

- 작업을 A/B/C로 깐깐하게 나누던 **분류표**. 모델이 알아서 분류를 잘하니, "단순 수정이면 바로, 복잡하면 계획부터"라는 *권유형*의 한 줄로 줄였다.

- 사실상 같은 일을 하던 **프론트·백엔드·DB 단순 개발 에이전트 넷**. "편집한 모든 줄은 맡은 작업과 직접 매핑돼야 한다"는 수술적인 변경 원칙만 공통으로 흡수시키고, `implementer` 에이전트 하나로 합쳤다.

- 한참 전에 꺼 둔 **배포 기능**. `deploy-*` 에이전트와 배포 스크립트는 호출해도 즉시 종료하도록 가드만 남겨 둔, 사실상 죽은 기능이었다.

그 결과 진입점으로 제공되는 문서(`CLAUDE.md`)도 152줄에서 84줄로 줄었다. 반대로 검증이나 권한 분리, 메모리 부분은 AI가 똑똑해질수록 *더* 중요했다. 확신할수록 객관적 검증이 필요하기 때문이다.

이 부분을 **두 번의 더 큰 제거** 과정으로 옮겼다.

## 메모리 공유 제거

[[harness-7-snowflake|7편]]에서 만든 동기화 기능을 제거했다. 데이터 조회와 기록 저장을 *공식 커넥터*가 맡기로 하면서, 직접 만들어 운영하던 부분이 통째로 중복이 되었기 때문이다. 그 부분에만 종속되어 있던 보조 모듈들도 함께 삭제했다. 청킹/마스킹/증분 마커와 같이 전에 공들였던 코드들이다.

```text 삭제된 파일
- run-harness-rag.mjs, set-harness-rag-secret.mjs
- memory-sync{,-trigger,-exclude}.mjs
- lib/memory-{sync-marker, chunker, scrubber}.mjs
→ .mcp.json: harness-rag 서버 제거 / SessionStart 핸들러 4→3
```

아까운 코드였지만, *중복은 부채*다. 같은 일을 두 곳이 하면 둘 다 관리해야 하고, 둘이 어긋나면 문제가 커질 수 있다. SessionStart 훅을 트리거 삼은 스크립트도 네 개에서 셋으로 줄었다.

## 코드 분석도 네이티브로 돌아가다

더 큰 결정은 [[harness-3-serena-proxy|3편]]의 코드 분석 도구(**Serena**)를 빼는 것이었다. 모델이 충분히 똑똑해지면서, 기본 도구(파일 읽기/검색)만으로도 코드 탐색이 잘 됐다. **외부 도구 하나가 주는 이득보다, 세션마다 외부 프로세스를 띄우는 부담이 더 커진 것**이다.

```json .mcp.json
// 제거 후, 빈 통로만 남긴다
{
  "mcpServers": {}   // [!code highlight]
}
```

Serena를 쓸 땐 토큰을 아끼려고 탐색에 계단식 정책까지 뒀었다. 먼저 심볼(**symbol**; 함수/클래스 같은 코드 단위)을 정확히 찾고, 안 되면 부분 일치로, 그래도 안 되면 파일 개요를 보고, 마지막에야 통째로 읽는 식이다. 그런데 모델이 똑똑해지자 그냥 `rg`(**ripgrep**; 빠른 텍스트 검색 방법)와 파일 읽기만으로도 코드를 잘 짚었다. 단계적인 코드 분석을 떠받치던 외부 도구가 사라져도 탐색력이 꺾이지 않은 것이다. 그래서 읽기 도구만 가지던 검토 에이전트, 계획 에이전트의 기본 검색을 보강하고, 외부 프로세스를 띄우는 과정을 제거했다.

## Serena로 인한 잔재도 치우기

여기서 한 가지가 더 걸렸다. 코드를 지운다고 *이미 각 PC에 깔린* 격리된 uv와 Serena 캐시(1기가가 넘었다)까지 사라지진 않는다. 그래서 PC마다 *딱 한 번씩* 도는 청소 스크립트를 붙였다.

```js scripts/serena-cleanup.mjs
if (existsSync(doneFlag)) return;          // 이 PC에서 이미 돌았으면 즉시 끝 [!code highlight]
// uv 캐시 중 serena로 "식별된" 것만 회수. 내용으로 확인하지, 경로만 보고 지우지 않는다
const SERENA_URL_RE = /oraios[\/\\]serena/i;
// ... 회수 끝나면
writeFileSync(doneFlag, new Date().toISOString());  // 완료 표시
process.exit(0);                                     // 어떤 경우에도 정상 종료
```

불변식이 까다로웠다. *출력을 내보내지 않고*(사용자 화면을 어지럽히지 않게 로그는 파일에만 쌓이게 함), *어떤 예외도 던지지 않고*(청소 스크립트가 도중에 실패해도 세션을 막지 않게 항상 `exit 0`), 완료 표시로 *한 번만* 돌 수 있게 했다. 그리고 다른 직원이 다른 용도로 쓰는 같은 uv의 패키지는 절대 건드리지 않는다. 그래서 경로만 보고 지우지 않고, 파일 *내용*에서 `oraios/serena` 흔적을 남긴 것들만 회수했다. 이 청소 스크립트 자체도 일회성인 작업이라 **다음 배포 과정에서 함께 지울 예정**이다.

## 결론

하네스는 **자동차의 운전 보조 장치**다. 운전 실력(모델 성능)이 늘면 어떤 보조는 떼어도 된다. 하지만 안전벨트와 브레이크 점검은 실력과 무관하게 계속 필요하다. 이 시리즈는 결국 그 분별의 기록이다. ***알아서 하는 일은 AI에 맡기고, 멋대로 건너뛸 수 있는 일은 더 단단히 잡는다.***

[[harness-3-serena-proxy|3편]]에서 똑똑한 우회(Stub Proxy)를 단순한 과정이 이겼던 것처럼, 여기서도 직접 만든 것을 표준 방법과 네이티브 기능들이 이겼다. **만드는 것만큼** ***지우는 것*** **도 엔지니어링**이라는 걸, 이 과정에서 가장 또렷이 배웠다.

여기까지가 한 하네스를 쌓고 덜어낸 기록이다. 그런데 덜어내고 나니 이제는 또 채울 부분이 생겼다. 지금까지는 *개발*만 받쳤지만, 기획/영업/디자인 같은 다른 영역도 받치려면 에이전트를 여럿 두고 일을 나눠야 한다. 그 멀티 에이전트를 다시 *벤치마킹*하는 데서 다음 이야기를 꺼내본다. 🌼
