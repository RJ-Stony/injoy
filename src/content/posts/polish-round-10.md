글 한 편에는 글자만 있는 것이 아니다. 코드도 있고, 다이어그램도 있고, 가끔은 표도 있다. 그런데 정작 이런 블록들은 그동안 가만히 놓여 있기만 했다. 다이어그램은 본문의 폭에 눌려서 작게만 보였고, 코드는 길어지면 글이 늘어질까 봐 주요 부분만 짧게 잘라서 넣었다. 표는 줄이 많아지면 어느 행을 보고 있었는지 금세 놓치게 되었다.

그래서 이번에는 텍스트보다 글 안의 이런 블록들이 더 잘 보이도록 손보았다. 그리고 시작하기 전에 한 가지 원칙을 정해 두었다. 무엇을 추가하든 [[wysiwyg-editor|글을 작성하는 화면]]에서도 만들고, 고치고, 지울 수 있어야 한다(**CRUD가 가능**)는 것이다.

## 작던 다이어그램을 크게 보기

가장 답답했던 것은 다이어그램이었다. 순서도 하나가 작게 그려지면, 글자가 너무 작아서 읽기 어려웠다. 그래서 다이어그램의 오른쪽 위에 작은 확대 버튼을 달고, 누르면 화면을 거의 채우는 모달로 확대되도록 했다. 이 모달 안에서는 휠로 확대하고 축소할 수 있고, 모바일에서는 두 손가락으로 키울 수 있으며, 오른쪽 아래의 버튼으로도 키우고 줄일 수 있다. [그래프 화면](/graph/)에서 사용하던 줌 방식을 그대로 가져온 것이다.

여기서 중요한 것은, 커서(또는 두 손가락의 중점) 아래에 있는 지점이 화면에서 제자리에 남도록 **위치를 다시 계산하는 함수**이다. 이 함수는 줌 배율(`scale`)을 바꾸기 전에 커서 아래에 있던 지점을 기억해 두고, 배율을 바꾼 뒤에 그 지점이 같은 화면 위치에 오도록 이동값(`t`)을 다시 맞춘다. 그래프에서 이미 검증한 수식이어서 그대로 옮겨 왔다.

```ts src/components/DiagramModal.astro
// 한 점(화면 좌표) 아래 지점이 제자리에 남도록 t를 재계산하는 표준 줌
const zoomAt = (clientX: number, clientY: number, target: number) => {
  const r = stage.getBoundingClientRect();
  const x = clientX - r.left;
  const y = clientY - r.top;
  const ns = clamp(target);
  const wx = (x - view.tx) / view.scale;
  const wy = (y - view.ty) / view.scale;
  view.scale = ns;
  view.tx = x - wx * ns; // [!code highlight]
  view.ty = y - wy * ns; // [!code highlight]
  apply();
};
```

이렇게 해 두면 휠을 굴려도 마우스가 가리키던 곳이 화면에서 튀지 않는다.

확대되는 모달은 별도의 라이브러리 없이 브라우저가 기본으로 제공하는 `<dialog>`로 만들었다. `showModal()` 한 줄만 호출하면 헤더 위에 모달이 나타나고, ESC로 닫는 동작, 바깥을 누르면 닫히는 동작, 뒤의 배경이 가려지는 동작까지 함께 따라온다. 다이어그램을 다시 그릴 때는 카드 썸네일과 똑같은 공용 렌더러를 사용한다. 확대되는 모달이라고 해서 다이어그램이 다른 색으로 그려지면 안 되기 때문이다.

## 다이어그램이 가끔씩 밀려 있었다

그렇게 다이어그램을 키워 두고 잘 보고 있었는데, 가끔 순서도가 옆으로 밀려서 마지막 노드가 잘려 보였다. 항상 그런 것이 아니라 어쩌다 한 번이었고, 새로고침을 하면 멀쩡해지기도 했다. 화면을 아무리 들여다보아도 원인이 잡히지 않았고, '가끔'이라는 말만이 단서였다.

원인은 글꼴이었다. 다이어그램을 그리는 mermaid는 노드의 크기를 정하기 위해 글자의 폭을 직접 잰다. 그런데 이 블로그가 사용하는 글꼴(Wanted Sans)은 외부에서 받아 오는 웹폰트이다. 그래서 첫 방문처럼 글꼴이 아직 도착하지 않았을 때 다이어그램을 그리면, mermaid는 임시로 적용된 기본 글꼴을 기준으로 노드의 크기를 잰다. 그 뒤에 **실제 글꼴이 뒤늦게 도착하면 글자의 폭이 달라지면서, 노드와 글자가 어긋나 다이어그램이 밀리게 된다.** 글꼴을 한 번 받아서 캐시해 둔 뒤에는 멀쩡하기 때문에, 이 문제가 간헐적으로만 나타났던 것이다.

고치는 방법은 한 줄에 가까웠다. 다이어그램을 그리기 전에 글꼴이 모두 도착할 때까지 기다리면 된다. 이때 사용한 `document.fonts.ready`는 지금 페이지에서 사용하는 글꼴이 모두 로드되면 완료되는 Promise이다.

```ts src/scripts/mermaid-render.ts
// 글꼴 로드 전에 그리면 폴백 글꼴 글자 폭으로 칸을 재 다이어그램이 어긋난다.
// 그리기 전에 글꼴 로드를 기다려 항상 같은 글꼴로 잰다.
try {
  if (document.fonts?.ready) await document.fonts.ready; // [!code highlight]
} catch {}
```

이 값을 기다린 뒤에 그리기 때문에, 이제는 첫 방문이든 새로고침이든 mermaid가 항상 실제 글꼴로 노드를 재고, 다이어그램도 밀리지 않는다. <u>눈으로는 찾지 못하던 어긋남의 원인이, 결국 글꼴을 기다리지 않은 한 줄에 있었다.</u>

## 코드 블록에 헤더를 달았다

코드 블록은 구조를 통째로 다시 잡았다. 위에 헤더 한 줄을 추가해서, 왼쪽에는 언어와 파일명을, 오른쪽에는 접기 버튼과 복사 버튼을 두었다.

가장 신경 쓴 것은 내부 스크롤이다. 코드가 길어도 블록 안에서만 스크롤되기 때문에, 이제는 **글의 흐름을 끊지 않고도 긴 코드를 그대로 담을 수 있다.** 그동안 코드를 짧게 잘라서 넣던 이유가 사라진 것이다.

헤더에 표시할 언어는 빌드 과정에서 이미 알 수 있었다. 코드 펜스에 적은 언어가 `pre` 요소의 `data-language`에 그대로 담겨 나오기 때문이다. 없는 것은 파일명이었다. 그래서 코드 펜스의 언어 뒤에 적은 글자를 파일명으로 읽어서 `data-title`에 담아 보내는 작은 변환기(transformer)를 빌드 과정에 추가했다. 예를 들어 ` ```ts src/foo.ts `처럼 적으면, `src/foo.ts`가 코드 블록 헤더의 파일명으로 표시된다.

```js astro.config.mjs
// 코드 펜스의 언어 뒤 메타(파일명)를 pre의 data-title로 실어 보낸다.
const fenceTitle = {
  name: 'injoy-fence-title',
  pre(node) {
    const raw = (this.options.meta?.__raw ?? '').trim();
    if (raw) node.properties['data-title'] = raw; // [!code highlight]
  },
};
```

줄을 하이라이트하거나 지우는 표시(`// [!code highlight]` 같은)는 코드의 주석에서 처리된다. 코드 펜스 뒤의 메타데이터와는 자리가 서로 다르기 때문에 충돌하지 않는다.

표도 함께 손보았다. 줄이 많은 표에서 보고 있던 행을 놓치지 않도록, 호버한 행에 은은한 하이라이트를 넣었다. 이 부분은 자바스크립트 없이 CSS 한 줄이면 충분했다.

```css src/styles/global.css
.prose table tbody tr:hover {
  background-color: color-mix(in srgb, var(--accent) 8%, transparent);
}
```

## 파일명을 달자, 저장할 때마다 사라졌다

여기까지는 순조로웠다. 문제는 그다음이었다.

파일명을 코드 블록의 헤더에 표시하는 것까지는 되었는데, 처음에 정한 원칙대로라면 그 파일명을 글을 작성하는 화면에서도 고칠 수 있어야 했다. [[wysiwyg-editor|보이는 대로 편집하는 에디터]]는 화면의 내용을 다시 마크다운으로 되돌려서 저장한다. 그래서 파일명을 단 코드 블록을 에디터에서 한 번 열었다가 저장해 보았더니, ` ```ts src/foo.ts `가 ` ```ts `로 돌아와 있었다. 파일명이 지워진 것이다.

[[polish-round-8|발행 대기를 없앤 글]]에서도 비슷한 사고가 있었다. 그때는 글을 고쳐서 저장하면 시리즈 정보가 사라졌다. 이번에도 같은 종류의 버그였다. 화면에서는 멀쩡한데, 저장하는 순간 내용의 일부가 사라지는 문제이다.

원인은 에디터가 사용하는 Milkdown에 있었다. Milkdown은 코드 블록을 다룰 때 **언어만 기억하고 그 뒤의 메타데이터(파일명)는 버리도록** 되어 있었다. 그래서 코드 블록의 내부 구조에 `meta`라는 칸을 하나 더 만들고, 읽을 때와 저장할 때 모두 파일명을 함께 처리하도록 기존의 정의를 덮어썼다. 추가한 곳은 세 군데뿐이다. 칸을 하나 만들고(`attrs`), 마크다운을 읽을 때 그 칸을 채우고(`parseMarkdown`), 저장할 때 다시 적는다(`toMarkdown`).

```ts src/scripts/milkdown-editor.ts
const codeBlockWithMeta = codeBlockSchema.extendSchema((prev) => (ctx) => {
  const base = prev(ctx);
  return {
    ...base,
    attrs: { ...base.attrs, meta: { default: '', validate: 'string' } }, // [!code ++]
    parseMarkdown: {
      match: base.parseMarkdown.match,
      runner: (state, node, type) => {
        state.openNode(type, { language: node.lang ?? '', meta: node.meta ?? '' }); // [!code ++]
        if (node.value) state.addText(node.value);
        state.closeNode();
      },
    },
    toMarkdown: {
      match: base.toMarkdown.match,
      runner: (state, node) => {
        state.addNode('code', undefined, node.content.firstChild?.text || '', {
          lang: node.attrs.language,
          meta: node.attrs.meta || undefined, // [!code ++]
        });
      },
    },
  };
});
```

이렇게 해서 코드 블록을 마크다운으로 되돌릴 때에도 파일명이 빠지지 않게 되었다. 그러고 나서 에디터의 코드 블록 위에 파일명을 적는 입력칸을 달았다. 이미지에 alt와 정렬 입력칸을 다는 방식과 똑같이, 코드 본문은 그대로 두고 헤더만 추가했다. 이제 글을 작성하는 화면에서 코드 블록을 넣고, 파일명을 적고, 비우고, 블록째 지우는 일을 모두 할 수 있다. 발행은 예전 그대로다. 화면 뒤에서 오가는 마크다운만 파일명을 함께 가지고 갈 뿐이다.

걱정되었던 점은 코드 블록이 글을 쓸 때 가장 많이 사용하는 블록이라는 것이었다. 입력칸을 잘못 추가하면 코드를 입력하는 것 자체가 망가질 수 있었다. 그래서 [[wysiwyg-editor|위지윅으로 바꿀 때]]처럼 왕복 검증을 거쳤다. 파일명을 넣고 저장했다가 다시 불러와도 그대로인지, 코드 본문은 문제없이 고쳐지는지를 하나씩 확인했다.

## 그 밖에 다듬은 것들

블록 외에도 자잘하게 손본 것들이 있다.

- **배포 완료 알림.** 글을 발행하고 '글 보러 가기'를 누르면 그 글의 페이지로 넘어가는데, 그 뒤에 사이트의 빌드가 끝났는지는 알 방법이 없었다. 이제는 어느 페이지에 있든, 글의 발행이 끝나면 화면 아래에 작은 알림이 잠깐 나타났다가 사라진다. 이 알림은 발행한 내 브라우저에서만 동작하기 때문에, 글을 읽으러 온 사람에게는 아무 일도 일어나지 않는다.

- **에디터 두 글을 시리즈로.** [[wysiwyg-editor|에디터를 통째로 바꾼 글]]과 [[slash-menu|슬래시 메뉴 글]]이 피드에 흩어져 있어서, '블로그 다듬기 기록' 시리즈의 맨 앞으로 모았다.

- **모바일 발행 문구.** 글을 작성하는 화면에서 발행 상태 문구가 버튼 위에 어정쩡하게 떠 있던 것을 왼쪽으로 옮겼다.

- **관계도와 태그 정리.** 글 사이의 연결을 한 번 훑어보면서, 지나치게 강한 연결은 낮추고 빠진 연결은 추가했다. 태그도 `blog`와 `블로그`처럼 같은 뜻인데 나뉘어 있던 것을 하나로 합쳤다.

블록 하나하나는 작지만, 글을 읽는 사람이 코드를 접어 두거나 다이어그램을 키워 보는 그 잠깐이 글을 덜 답답하게 만든다고 생각한다. 다음에는 이 블록들을 글을 작성하는 화면에서 더 매끄럽게 다루는 방법을 살펴볼 것 같다. 🌱
