[그래프](/graph/) 화면은 글을 점(**노드**)으로, 글 사이 연결을 선(**엣지**)으로 그린다. 점들의 자리는 미리 정해 둔 게 아니라 **시뮬레이션**(force simulation; 점끼리 밀어내고 연결선이 잡아당기는 힘을 반복 계산해 배치를 정하는 방식)으로 매번 계산한다. 그런데 페이지에 들어가거나 새로고침할 때마다, 점들이 한참 동안 눈 앞에서 튀다가 자리를 잡았다. 계속 거슬리는 부류의 문제였다.

## 어떤 게 계속 튀었나

증상은 두 가지였다. 하나는 **들어갈 때마다** 점들이 펄럭이며 퍼지는 것. 또 하나는 자리를 잡은 뒤에도 **마우스를 올리거나 점을 끌 때마다** 다시 꿈틀대는 것이었다.

처음엔 헤드리스 브라우저(headless browser; **화면 없이 코드로만 돌리는 브라우저**)로 측정해 봤는데, "이미 멈춰 있다"고 나와있어서 한참을 헤맸다. 원인은 단순했다. **헤드리스에는 마우스가 없어서**, 마우스를 올릴 때 도는 코드가 아예 실행되지 않았던 것이다. 내가 실제로 마우스를 움직이면 다른 일이 벌어지고 있었다.

## 마우스만 올려도 꿈틀대던 것

점 위에 커서가 닿을 때마다 시뮬레이션을 **통째로 다시 깨우고** 있었기 때문이다. 강조 표시(hover 하이라이트)만 다시 그리면 되는데, 계산을 처음부터 다시 돌렸다. 키보드로 탐색할 때는 일부러 다시 그리기만 했는데, 마우스 hover만 시뮬레이션을 깨우는 *불일치 문제*가 있었다.

```js src/pages/graph.astro
// hover는 강조만 다시 그린다(물리 wake 금지). 키보드 탐색과 같은 방식.
if (n !== hovered) { hovered = n; /* 툴팁 갱신 */ wake(); }   // [!code --]
if (n !== hovered) { hovered = n; /* 툴팁 갱신 */ draw(); }   // [!code ++]
```

`wake()`는 시뮬레이션을 다시 돌리는 함수고, `draw()`는 지금 상태를 한 번 다시 그리기만 한다. hover는 그저 어느 점을 강조할지만 바뀌는 일이라 `draw()`로 충분했다.

## 진짜 원인은 점점 잦아드는 과정이 없던 것

그런데 hover를 고쳐도 *들어갈 때마다, 그리고 점을 드래그할 때마다* 튀는 건 그대로였다. 이게 더 깊은 문제였다. 우리 시뮬레이션엔 **잦아드는 과정이 없었다.**

시뮬레이션은 점끼리 밀어내고(척력) 연결선이 당기는(스프링) 힘을 매 프레임 속도에 더한다. 그런데 힘이 셀수록 노드가 제자리를 *지나쳐 버리고*(overshoot), 도로 당겨지고, 또 지나치고, 이 왕복이 바로 출렁임이었다. 감쇠(마찰)만으론 이 진동이 천천히 줄어 한참 눈에 보였다. 게다가 점을 끌어 시뮬레이션을 다시 깨우면 매번 **처음의 풀 에너지**로 되돌아가 또 출렁였고, 화면 경계(벽)에 눌린 점은 속도가 죽지 않아 가장자리에서 영영 떨리게 되었다.

## 식으면서 멈추게 했다

해법은 [d3-force](https://d3js.org/d3-force/simulation)가 쓰는 **냉각**(alpha cooling)이었다. `alpha`라는 *온도* 같은 값을 두고, 모든 힘을 거기에 곱한 뒤 매 틱마다 조금씩 줄였다. 처음엔 활발히 움직이다가 `alpha`가 0에 가까워지면 힘도 0이 되어 **스르륵 멈춘다.** 진동할 새 없이 잦아드는 것이다.

> `alpha`는 매 틱마다 정해진 비율(alphaDecay)만큼 0을 향해 줄고, 힘은 `alpha`에 비례한다. 점을 끄는 동안엔 `alpha`를 조금 데워 두어서 이웃 노드들이 계속 따라오고, 놓으면 다시 잦아든다.

```js src/pages/graph.astro
// 힘을 alpha로 스케일 (alpha가 줄면 힘도 함께 잦아든다)
const f = (REPULSION / d2) * alpha;                         // [!code ++]
// 벽에 닿으면 그 방향 속도를 죽인다 (안 그러면 가장자리에서 영영 튄다)
if (n.x <= -BX || n.x >= BX) n.vx = 0;                      // [!code ++]
// 냉각: 드래그 중엔 0.3으로 데우고, 놓으면 0으로 식는다
alpha += ((dragging ? 0.3 : 0) - alpha) * ALPHA_DECAY;      // [!code ++]
```

점을 끌고 있는 동안엔 `alpha`가 0.3 언저리로 *데워진 채* 머물러 주변 점들이 부드럽게 따라오고, 손을 놓으면 0으로 식으며 잔잔해진다.

```mermaid
flowchart LR
    A["진입·드래그 - alpha 높음(활발)"] --> B["매 틱마다의 힘 × alpha, alpha 감소"]
    B --> C["alpha → 0 - 힘도 0, 스르륵 정지"]
```

애니메이션은 예전 그대로 둔다. 점들이 자리를 잡아 가는 모습은 여전히 보이되, 이제 *식으며* 가라앉아 튀지 않는다. 끌면 주변이 부드럽게 따라오고, 놓으면 다시 잔잔해진다. d3 같은 큰 라이브러리가 진작에 이 냉각을 **기본으로 두는 데**는 이유가 있었다.

## 드래그할 때 가끔씩 튕기던 마지막 하나

냉각 과정을 넣고도, 점을 *이리저리 끌다 보면* 가끔 하나가 화면 밖으로 튕겨 나갔다. 원인은 **척력의 모양**에 있었다. 두 점이 밀어내는 힘은 거리의 제곱에 반비례한다(`척력 ∝ 1/거리²`). 그래서 드래그하다 두 점이 아주 가까워지는 순간, 힘이 폭발적으로 커져 한 프레임 만에 점이 멀리 *쏘아진다.* 평소엔 잔잔하다가 *가끔* 튀던 게 이 때문이었다. (**수학을 배워야하는 이유...**)

그래서 한 프레임에 점이 움직일 수 있는 거리에 **상한**을 뒀다. 힘이 아무리 치솟아도, 한 번에 그 이상은 못 움직인다.

```js src/pages/graph.astro
const MAX_V = 26; // 한 틱 당 최대 이동 거리(속도 상한)
// ...적분 직전...
const sp = Math.hypot(n.vx, n.vy);                       // [!code ++]
if (sp > MAX_V) { n.vx *= MAX_V / sp; n.vy *= MAX_V / sp; }  // [!code ++]
n.x += n.vx;
n.y += n.vy;
```

속도(`sp`)가 상한을 넘으면 방향은 그대로 두고 크기만 상한으로 줄인다. 이러니 가까운 두 점이 순간적으로 큰 힘을 주고받아도, 점이 한 프레임에 휙 날아가지 않고 한 칸씩만 천천히 물러난다. 냉각 과정이 *전체적인* 출렁임을 잡았다면, 이 상한은 ***순간적인*** **튐을 막는 안전장치**다.

## 결론

고치고 나서 두 가지를 알게 되었다. 하나는 헤드리스 검증이 "괜찮다"고 해도 **사람이 실제로 만지는 상황**은 다를 수 있다는 것. 마우스가 없으니 hover 문제가 안 잡혔고, 그 탓에 한참 엉뚱한 데를 손봤다. 또 하나는, 흔들림을 없애는 부분이 애니메이션을 *지우는 것*이 아니라 **잘 식게 만드는 것**이었다는 점이다. 처음엔 그래프를 아예 정착된 채로 띄워도 봤지만, 움직임이 주는 생동감까지 잃었다. 결국 답은 움직이되 *반드시 멈추는* 장치를 더하는 쪽이었다. 🍀
