[그래프](/graph/) 화면은 글을 점으로, 글 사이 연결을 선으로 그린다. 점들의 자리는 미리 정해 둔 게 아니라 **힘 시뮬레이션**(force simulation; 점끼리 밀어내고 연결선이 잡아당기는 힘을 반복 계산해 배치를 정하는 방식)으로 매번 계산한다. 그런데 페이지에 들어가거나 새로고침할 때마다, 점들이 한참 동안 눈앞에서 *출렁이다가* 자리를 잡았다. 한 번 보이면 계속 거슬리는 부류였다.

## 무엇이 출렁였나

증상은 두 가지였다. 하나는 **들어갈 때마다** 점들이 펄럭이며 퍼지는 것. 또 하나는 자리를 잡은 뒤에도 **마우스를 올릴 때마다** 다시 꿈틀대는 것이었다.

처음엔 헤드리스 브라우저(headless browser; 화면 없이 코드로만 돌리는 브라우저)로 측정해 봤는데, "이미 멈춰 있다"고 나왔다. 한참 헤맸다. 원인은 단순했다. **헤드리스에는 마우스가 없어서**, 마우스를 올릴 때 도는 코드가 아예 실행되지 않았던 것이다. 사람이 실제로 마우스를 움직이면 다른 일이 벌어지고 있었다.

## 두 번째 출렁임부터

마우스를 올릴 때마다 다시 꿈틀댄 건, 점 위에 커서가 닿을 때마다 시뮬레이션을 **통째로 다시 깨우고** 있었기 때문이다. 강조 표시(hover 하이라이트)만 다시 그리면 되는데, 물리 계산을 처음부터 다시 돌렸다. 키보드로 탐색할 때는 일부러 다시 그리기만 했는데, 마우스 hover만 시뮬을 깨우는 *불일치*가 있었다.

```js src/pages/graph.astro
// hover는 강조만 다시 그린다(물리 wake 금지). 키보드 탐색과 같은 방식.
if (n !== hovered) { hovered = n; /* 툴팁 갱신 */ wake(); }   // [!code --]
if (n !== hovered) { hovered = n; /* 툴팁 갱신 */ draw(); }   // [!code ++]
```

`wake()`는 물리 시뮬을 다시 돌리는 함수고, `draw()`는 지금 상태를 한 번 다시 그리기만 한다. hover는 그저 어느 점을 강조할지만 바뀌는 일이라 `draw()`로 충분했다.

## 진짜 원인은 따로 있었다

hover를 고쳐도 *들어갈 때마다 출렁이는 것*은 그대로였다. 이게 본질이었다. 들어올 때 시뮬레이션을 **화면에 띄운 채로** 돌리고 있었던 것이다. 매 프레임마다 점을 조금씩 움직이고 다시 그리길 반복하니, 자리를 잡아 가는 과정이 고스란히 출렁임으로 보였다.

```mermaid
flowchart LR
    A["페이지 진입"] --> B["rAF 루프: 매 프레임 조금 움직이고 다시 그림"]
    B --> C["자리잡는 과정이 화면에 보임 = 출렁임"]
```

이걸 어떻게 다루는 게 정석인지 찾아봤다. 그래프 레이아웃의 사실상 표준인 [d3-force](https://d3js.org/d3-force/simulation)는 이런 경우를 위해 **정적 레이아웃**(static layout)을 문서로 안내하고 있었다. 핵심은 이렇다.

> 애니메이션을 보여 주지 않으려면, 시뮬레이션을 멈춰 둔 채 `tick()`을 원하는 횟수만큼 미리 돌린 뒤 **한 번만** 그린다.

[d3의 정적 포스 그래프 예제](https://observablehq.com/@d3/static-force-directed-graph)가 바로 그 방식이다. 기본 반복 횟수는 300번이고(수렴할 때까지 도는 자연스러운 횟수), 점이 아주 많으면 화면이 멈추지 않게 워커(worker; 화면과 분리된 별도 계산 스레드)에서 돌리라고도 한다. 우리 그래프는 d3를 쓰진 않지만 직접 만든 같은 계열(velocity Verlet)의 시뮬레이션이라, *기법*은 그대로 가져올 수 있었다.

## 미리 다 돌리고, 한 번만 그린다

그래서 들어올 때는 시뮬레이션을 화면에서 굴리지 않기로 했다. 미리 정해진 횟수만큼 계산을 끝내고, **정착된 모습만 한 번** 그린다. 마침 '동작 줄이기'(reduced motion)를 켠 사용자에게는 이미 이렇게 하고 있어서, 그 방식을 모두에게 적용한 셈이다.

```js src/pages/graph.astro
const restart = () => {
  readColors(); resize(); nodes.forEach(seed);
  wake();                                       // [!code --]
  // 미리 다 돌려 정착된 좌표만 한 번 그린다(화면에서 굴리지 않음)
  const calmEnergy = Math.max(0.5, nodes.length * 0.05);  // [!code ++]
  for (let i = 0; i < 600; i++) {               // [!code ++]
    tick();                                     // [!code ++]
    const energy = nodes.reduce((s, n) => s + Math.abs(n.vx) + Math.abs(n.vy), 0);  // [!code ++]
    if (energy < calmEnergy) break;             // [!code ++]
  }                                             // [!code ++]
  fitToBbox(); draw();                          // [!code ++]
};
```

빨간 줄이 옛 방식(`wake()`로 화면에 시뮬을 띄워 돌림)이고, 초록 줄이 새 방식이다. **결국 점이 다 자리 잡은 다음에야 화면에 그린다.** 점이 멈출 때까지(또는 최대 600번까지) 계산을 돌리고, 그제야 전체를 한 번 그린다. 들어오는 사람은 처음부터 정착된 그래프를 본다.

```mermaid
flowchart LR
    A["페이지 진입"] --> B["시뮬을 미리 N번 계산(화면엔 안 그림)"]
    B --> C["정착된 좌표를 한 번만 그림"]
    C --> D["출렁임 없이 바로 보임"]
```

손으로 점을 끌 때만 예전처럼 실시간으로 따라 움직이게 두었다. 그건 내가 직접 옮기는 중이라 자연스러운 움직임이고, *들어올 때마다 멋대로 출렁이는 것*과는 다르다.

## 돌아보면

고치고 나서 두 가지를 다시 새겼다. 하나는 헤드리스 측정이 "괜찮다"고 해도 **사람이 실제로 만지는 상황**은 다를 수 있다는 것. 마우스가 없으니 hover 출렁임이 안 잡혔고, 그 탓에 한참 엉뚱한 데를 봤다. 또 하나는, 보기 좋은 애니메이션이라도 **매번 강제로 보여 주면 피로가 된다**는 것이다. 자리 잡는 과정은 한 번이면 족하고, 그마저도 안 보여 주는 편이 깔끔했다. 만드는 것보다 *덜 움직이게 만드는 것*이 답일 때가 있다. 😎
