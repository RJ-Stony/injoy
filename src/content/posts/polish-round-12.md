[그래프](/graph/) 화면은 글을 점(**노드**)으로, 글 사이의 연결을 선(**엣지**)으로 그린다. 노드들의 자리는 미리 정해 둔 것이 아니라 **시뮬레이션**(force simulation; 노드끼리 밀어내고 엣지가 잡아당기는 힘을 반복 계산해 배치를 정하는 방식)으로 매번 계산한다. 그런데 페이지에 들어가거나 새로고침할 때마다, 노드들이 한참 동안 눈앞에서 튀다가 자리를 잡았다. 볼 때마다 신경이 쓰이는 문제였다.

## 계속 튀던 두 가지 증상

증상은 두 가지였다. 하나는 페이지에 들어갈 때마다 노드들이 펄럭이며 퍼지는 것이었다. 다른 하나는 자리를 잡은 뒤에도 노드에 **호버하거나 노드를 끌 때마다** 다시 꿈틀대는 것이었다.

처음에는 **헤드리스 브라우저**(headless browser; 화면 없이 코드로만 실행하는 브라우저)로 측정해 보았는데 "이미 멈춰 있다"고 나와서 한참을 헤맸다. 원인은 단순했다. 헤드리스 브라우저에는 마우스가 없어서, 마우스를 올릴 때 실행되는 코드가 아예 동작하지 않았던 것이다. 내가 실제로 마우스를 움직이면 측정 결과와는 다른 일이 벌어지고 있었다.

## 마우스를 올리기만 해도 꿈틀대던 노드

노드 위에 커서가 닿을 때마다 시뮬레이션을 처음부터 다시 시작하고 있었기 때문이다. 호버할 때는 하이라이트만 다시 그리면 되는데, 배치 계산까지 다시 시작했다. 키보드로 탐색할 때는 처음부터 화면만 다시 그리도록 해 두었으니, 마우스 호버만 시뮬레이션을 다시 시작하는 불일치가 있었던 것이다. 아래의 diff가 이 부분을 고친 코드이다.

```js src/pages/graph.astro
// hover는 강조만 다시 그린다(물리 wake 금지). 키보드 탐색과 같은 방식.
if (n !== hovered) { hovered = n; /* 툴팁 갱신 */ wake(); }   // [!code --]
if (n !== hovered) { hovered = n; /* 툴팁 갱신 */ draw(); }   // [!code ++]
```

`wake()`는 시뮬레이션을 다시 실행하는 함수이고, `draw()`는 지금 상태를 한 번 다시 그리기만 한다. 호버는 어느 노드를 하이라이트할지만 바뀌는 일이므로, `draw()`로 충분했다.

## 진짜 원인은 잦아드는 과정이 없던 것

그런데 호버를 고치고 나서도 들어갈 때와 노드를 드래그할 때마다 튀는 것은 그대로였다. 이쪽이 더 깊은 문제였다. 이 시뮬레이션에는 **잦아드는 과정이 없었다.**

시뮬레이션은 노드끼리 밀어내는 힘(척력)과 엣지가 잡아당기는 힘(스프링)을 매 프레임 속도에 더한다. 그런데 힘이 셀수록 노드가 제자리를 지나쳐 버리고(overshoot), 도로 당겨지고, 또 지나치기를 반복한다. 이 왕복이 출렁임이었다. 감쇠(마찰)만으로는 이 진동이 천천히 줄어들어서 한참 동안 눈에 보였다. 게다가 노드를 끌어서 시뮬레이션을 다시 시작하면 매번 처음의 풀 에너지로 되돌아가 또 출렁였고, 화면 경계(벽)에 눌린 노드는 속도가 줄어들지 않아서 가장자리에서 계속 떨렸다.

## 식으면서 멈추게 했다

이 문제의 해법은 [d3-force](https://d3js.org/d3-force/simulation)가 사용하는 **냉각**(alpha cooling)이었다. `alpha`라는 온도 같은 값을 두고 모든 힘에 이 값을 곱한 뒤, 매 프레임마다 조금씩 줄였다. 처음에는 활발하게 움직이다가 `alpha`가 0에 가까워지면 힘도 0이 되어서 서서히 멈춘다. 진동할 틈 없이 잦아드는 것이다.

> `alpha`는 매 프레임마다 정해진 비율(alphaDecay)만큼 0을 향해 줄고, 힘은 `alpha`에 비례한다. 노드를 끄는 동안엔 `alpha`를 조금 데워 두어서 이웃 노드들이 계속 따라오고, 놓으면 다시 잦아든다.

아래 코드는 이 냉각을 적용한 부분이다. 먼저 힘에 `alpha`를 곱해서 `alpha`가 줄면 힘도 함께 줄어들게 했다. 그리고 벽에 닿은 노드는 그 방향의 속도를 0으로 만들어서, 가장자리에서 계속 튀는 일을 막았다. 마지막으로 드래그하는 동안에는 `alpha`를 0.3으로 데우고, 놓으면 0으로 식도록 했다.

```js src/pages/graph.astro
// 힘을 alpha로 스케일 (alpha가 줄면 힘도 함께 잦아든다)
const f = (REPULSION / d2) * alpha;                         // [!code ++]
// 벽에 닿으면 그 방향 속도를 죽인다 (안 그러면 가장자리에서 영영 튄다)
if (n.x <= -BX || n.x >= BX) n.vx = 0;                      // [!code ++]
// 냉각: 드래그 중엔 0.3으로 데우고, 놓으면 0으로 식는다
alpha += ((dragging ? 0.3 : 0) - alpha) * ALPHA_DECAY;      // [!code ++]
```

노드를 끌고 있는 동안에는 `alpha`가 0.3 언저리로 데워진 채 유지되기 때문에 주변 노드들이 부드럽게 따라오고, 손을 놓으면 0으로 식으면서 잔잔해진다. 이 흐름을 그리면 아래와 같다.

```mermaid
flowchart LR
    A["진입·드래그 - alpha 높음(활발)"] --> B["매 틱마다의 힘 × alpha, alpha 감소"]
    B --> C["alpha → 0 - 힘도 0, 스르륵 정지"]
```

모션은 예전 그대로 두었다. 노드들이 자리를 잡아 가는 모습은 여전히 보이되, 이제는 식으면서 가라앉기 때문에 튀지 않는다. d3 같은 큰 라이브러리가 이 냉각을 진작부터 기본으로 두는 데에는 이유가 있었던 것이다.

## 드래그할 때 가끔 튕기던 마지막 하나

냉각을 넣고 나서도, 노드를 이리저리 끌다 보면 가끔 하나가 화면 밖으로 튕겨 나갔다. 원인은 척력의 모양에 있었다. 두 노드가 밀어내는 힘은 거리의 제곱에 반비례한다(`척력 ∝ 1/거리²`). 그래서 드래그하다가 두 노드가 아주 가까워지는 순간, 힘이 폭발적으로 커져서 한 프레임 만에 노드가 멀리 날아갔다. 평소에는 잔잔하다가 가끔 튀던 것이 이 때문이었다. (수학을 배워야 하는 이유…)

그래서 한 프레임에 노드가 움직일 수 있는 거리에 상한을 두었다. 힘이 아무리 커져도 한 번에 그 이상은 움직이지 못한다. 아래 코드에서 속도 `sp`가 이 상한을 넘으면, 방향은 그대로 두고 크기만 상한으로 줄인다.

```js src/pages/graph.astro
const MAX_V = 26; // 한 틱 당 최대 이동 거리(속도 상한)
// ...적분 직전...
const sp = Math.hypot(n.vx, n.vy);                       // [!code ++]
if (sp > MAX_V) { n.vx *= MAX_V / sp; n.vy *= MAX_V / sp; }  // [!code ++]
n.x += n.vx;
n.y += n.vy;
```

이렇게 하면 가까운 두 노드가 순간적으로 큰 힘을 주고받아도, 노드가 한 프레임에 휙 날아가지 않고 한 칸씩만 천천히 물러난다. 냉각이 전체적인 출렁임을 잡았다면, 이 상한은 **순간적인 튐을 막는 안전 장치**이다.

## 결론

고치고 나서 두 가지를 알게 되었다. 하나는 헤드리스 검증이 "괜찮다"고 해도 사람이 실제로 만지는 상황은 다를 수 있다는 것이다. 마우스가 없어서 호버 문제가 잡히지 않았고, 그 탓에 한참 엉뚱한 곳을 손보았다. 다른 하나는 흔들림을 없애는 일이 모션을 지우는 것이 아니라 잘 식게 만드는 일이었다는 것이다. 처음에는 그래프를 아예 정착된 상태로 표시해 보기도 했지만, 움직임이 주는 생동감까지 사라졌다. <u>결국 답은 움직이되 반드시 멈추는 장치를 더하는 쪽이었다.</u> 🍀
