이 블로그는 마크다운 파일 하나만 추가하면 곧 글이 올라가는 단순한 구조다. 그런데 정작 글을 쓰는 화면은 그 단순함과 거리가 멀었다. 왼쪽 칸에 `##`와 `>`와 백틱을 직접 입력하고, 미리보기로 결과를 확인하는 식이었다. 익숙해지면 빠르지만 문법을 머릿속에 담고 있어야 했다. Notion이나 다른 에디터의 매끄러움과는 분명히 달랐다.

그래서 이번에 글쓰기 화면을 통째로 바꿨다. 마크다운 기호를 직접 치는 대신, 보이는 그대로 편집하는 위지윅(WYSIWYG) 방식이다.

## 보이는 대로 쓰기

새 에디터는 Milkdown으로 만들었다. 화면을 그리는 편집기 엔진(ProseMirror) 위에, 마크다운을 읽고 쓰는 remark를 얹은 구조다. 그래서 화면에는 제목이 제목으로, 인용이 인용으로 보이지만 속에는 여전히 마크다운이 들어 있다. `**굵게**`라고 치면 별표가 사라지면서 글자가 굵어진다. Notion에서 쓰던 그 느낌 그대로다.

> [!NOTE]
> Milkdown은 완성된 에디터라기보다 에디터를 조립하는 부품에 가깝다. 표, 코드 블록, 수식 같은 기능을 플러그인으로 하나씩 끼워 넣어 Injoy에 맞는 편집기를 짜게 되었다.

이 무거운 에디터는 방문자에게는 전혀 보이지 않는다. 글쓰기 화면(`/write`)에서만 동적 import(필요한 순간에만 코드를 불러오는 방식)로 불러오기 때문이다.

```ts
// 글쓰기 화면이 실제로 열렸을 때만 로드된다
const { bootEditor } = await import('../scripts/milkdown-editor');
bootEditor(document.querySelector('#editor'));
```

읽으러 온 사람에게는 예전과 똑같이 정적 HTML만 보인다.

## 발행 과정은 건드리지 않았다

가장 신경 쓴 부분은 따로 있다. 발행 과정을 하나도 수정하고 싶지 않았다. 글 점검과 연결성 제안, 커밋까지 이미 잘 돌아가는 구조를, 편집기를 바꾼다고 수정할 수는 없었다.

그래서 textarea만 건드리게 되었다. 에디터에서 무엇을 하든 그 결과를 마크다운으로 바꿔 화면 뒤편의 `#fm-body` textarea로 흘려보낸다. 발행도 점검도 연결 제안도 예전처럼 이 textarea 값만 읽는다. 편집기는 갈아 끼웠지만 발행 시점에서 바라보는 건 그대로 둔 셈이다.

코드로는 한 줄이다. 에디터 내용이 바뀔 때마다 마크다운으로 직렬화(화면에 보이는 내용을 글자 데이터로 바꾸는 일)해서 흘려보내는 게 전부다.

```ts src/scripts/milkdown-editor.ts
// 에디터가 바뀔 때마다 마크다운으로 직렬화해 textarea로 보낸다
opts.onChange(normalizeMarkdown(editor.action(getMarkdown())));
```

`getMarkdown()`이 화면을 마크다운 문자열로 되돌리고, `normalizeMarkdown()`이 그 결과를 다듬고, `onChange`가 textarea에 써 넣는다. 발행 쪽은 이 코드의 존재조차 모른다.

```mermaid
flowchart LR
    A[위지윅 편집] --> B[마크다운으로 변환]
    B --> C[숨은 textarea]
    C --> D[점검·연결 제안]
    D --> E[커밋 & 배포]
```

덕분에 발행 과정은 자기 밑에서 에디터가 바뀐 줄도 모른다.

## 비표준 문법을 지키는 일

진짜 까다로운 건 따로 있었다. 위지윅은 화면의 내용을 다시 마크다운으로 풀어내는데, 이 과정에서 Injoy만의 비표준 문법이 쉽게 깨졌다.

| 문법              | 지키는 방법                   |
| --------------- | ------------------------ |
| 수식 `$...$`      | 전용 수식 플러그인이 노드(편집기가 다루는 내용 조각)로 보존       |
| 다이어그램·각주·이모지    | 표준 규칙으로 그대로 왕복           |
| 콜아웃 `> [!NOTE]` | 직렬화할 때 끼어든 이스케이프를 되돌려 복원 |
| 위키링크 `[[슬러그]]`  | 위와 같은 방식으로 복원            |

콜아웃과 위키링크는 마크다운으로 풀 때 대괄호 앞에 백슬래시가 끼어드는(이런 끼어듦을 이스케이프라 한다) 문제가 있었다. 이걸 되돌리는 보정을 넣되 코드블록과 인라인 코드 안에서는 절대 손대지 않도록 막았다.

그 보정은 코드 단위로 돈다. 코드펜스(코드블록을 여닫는 표시 줄)를 만나면 닫는 펜스까지 한 줄도 손대지 않고 그대로 흘려보내고, 코드 바깥에서만 위키링크와 콜아웃 마커를 되살린다.

```ts src/scripts/milkdown-editor.ts
export function normalizeMarkdown(md: string): string {
  const lines = md.split('\n');
  let fence: string | null = null;
  return lines
    .map((line) => {
      const fenceTok = line.match(/^\s*(`{3,}|~{3,})/)?.[1];
      if (fence) {
        // 코드펜스 안, 닫는 펜스를 만나기 전까지 전부 그대로
        if (fenceTok && fenceTok[0] === fence[0] && fenceTok.length >= fence.length) fence = null;
        return line; // [!code highlight]
      }
      if (fenceTok) { fence = fenceTok; return line; } // [!code highlight]
      // 코드 밖 줄에서만 보정한다
      return restoreWikiOutsideInlineCode(line).replace(CALLOUT_LINE, '$1[$2]');
    })
    .join('\n');
}
```

`fence` 변수가 핵심이다. 백틱 세 개로 코드블록을 여는 표시(펜스)를 만나면 그걸 기억해 두었다가, 짝이 되는 닫는 표시가 나올 때까지 그 안의 모든 줄을 손대지 않고 그대로 내보낸다. 위에서 강조한 두 줄이 그 '건드리지 않는 구간'이라, 코드 안에 적어 둔 `[[대괄호]]`나 정규식(문자열에서 패턴을 찾는 규칙) 예시는 보정에서 빠진다.

인라인 코드(문장 속에 백틱으로 감싼 짧은 코드)는 한 줄 안에 섞여 들어오니 따로 다룬다. 줄을 백틱 스팬 기준으로 쪼갠 뒤, 코드가 아닌 조각에서만 이스케이프를 되돌린다.

```ts
function restoreWikiOutsideInlineCode(text: string): string {
  return text
    .split(/(`+[^`]*`+)/) // 괄호가 있어 구분자(인라인 코드)도 배열에 남는다
    .map((seg, i) => (i % 2 === 1 ? seg : seg.replace(/\\\[\\\[/g, '[[').replace(/\\\]\\\]/g, ']]')))
    .join('');
}
```

한 줄을 인라인 코드(백틱) 기준으로 조각내면, 코드가 아닌 부분과 코드인 부분이 번갈아 나온다. 이 중 코드가 아닌 부분에서만 `\[\[`를 `[[`로 되돌리니, 코드 안에 일부러 쓴 백슬래시 예시는 그대로 살아남는다.

> [!WARNING]
> 이 예외를 빠뜨리면 코드 안에 쓴 대괄호까지 보정 대상이 되어 멀쩡한 코드가 망가진다. 처음엔 실제로 그렇게 짰다가 코드가 손상되는 걸 발견하고 급히 막았다.

## 빌드가 통과한다고 안심할 수 없는 코드

새 에디터로 만들면 데이터가 깨지기 쉬워서 본 코드에 합치기 전에 적대적인 리뷰 에이전트를 한 번 돌렸다. **(Claude Code의 ultracode 모드)** 여러 에이전트가 작정하고 흠을 찾는 방식인데, 여기서 눈으로는 놓칠 뻔한 데이터 손상 두 문제가 걸렸다. 그중 하나가 방금 말한 코드 안 대괄호 보정 문제였다.

빌드는 멀쩡히 통과하는데 배포하고 나서야 결과물이 틀어지는, 조용한 부류의 버그였다[^1]. 직렬화처럼 입력과 출력이 같아야 하는 코드일수록, 빌드가 통과했다는 안도감이 오히려 위험하다는 것을 알게 되었다.

[^1]: 그래서 이런 코드는 사람 한 명의 눈보다, 서로 물고 늘어지는 여러 시선이 낫다고 느꼈다.

## 남은 것

슬래시(`/`) 메뉴는 아직 없다. 지금은 모바일에서도 안전한 툴바로 대신하고 있다. 콜아웃 맨 앞에서 글자를 지우면 숨은 마커가 같이 지워져서 발행할 때 평범한 인용으로 강등되는 자잘한 문제도 남아 있다. 천천히 고쳐 갈 일이다.

쓰는 것은 확실히 나아졌다. 각 요소가 실제로 어떻게 보이는지는 [[markdown-styleguide]]에 모아 두었고, 글을 올리는 전체 방법은 [[how-to-write]]에 적어 두었다. 결국 글쓰기를 가로막는 마찰을 줄이는 게 이 블로그의 거의 전부고, 이번엔 쓰는 화면 차례였을 뿐이다. 🌱
