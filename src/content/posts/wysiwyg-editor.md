이 블로그는 마크다운 파일 하나만 추가하면 글이 올라가는 단순한 구조였다. 그런데 정작 글을 작성하는 화면은 그 단순함과 거리가 멀었다. `##`와 `>`와 백틱 같은 것을 직접 입력하고, 미리보기로 결과를 일일이 확인해야 했다. 익숙해지면 빠르겠지만, 마크다운 문법을 머릿속에 담고 있어야 했다. **Notion이나 다른 에디터의 매끄러움**과는 분명히 달랐다.

그래서 이번에는 글쓰기 과정을 통째로 바꾸었다. 마크다운 문법을 직접 작성하는 대신, 화면에 보이는 모습 그대로 편집하는 **위지윅**(WYSIWYG; What You See Is What You Get의 줄임말) 방식을 도입하게 되었다.

## 보이는 대로 쓰기

새 에디터는 Milkdown으로 만들었다. 화면을 그리는 에디터 엔진(ProseMirror) 위에, 마크다운을 읽고 쓰는 remark를 추가한 구조이다. 그래서 화면에는 제목이 제목으로, 인용이 인용으로 보이지만 속에는 여전히 마크다운 문법이 들어 있다. `**굵게**`라고 입력하면 별표 기호는 사라지면서 글자가 굵어진다. Notion에서 쓰던 그 느낌을 그대로 가져오려고 노력했다.

> [!NOTE]
> Milkdown은 완성된 에디터라기보다 **에디터를 조립하는 부품**에 가깝다. 표, 코드 블록, 수식 같은 기능을 플러그인으로 하나씩 추가해 블로그에 맞는 에디터를 만들게 되었다.

## 읽는 사람에게는 보이지 않게

플러그인을 하나씩 추가한 만큼 에디터는 무거워졌다. 이 무거운 에디터는 **방문자에게는 전혀 보이지 않는다**. 글을 작성하는 화면(`/write`)에서만 동적으로 import(필요한 순간에만 코드를 불러오는 방식)하기 때문이다. 아래 코드는 이 화면이 실제로 열렸을 때만 에디터 코드를 로드하는 부분이다.

```ts
// 글쓰기 화면이 실제로 열렸을 때만 로드된다
const { bootEditor } = await import('../scripts/milkdown-editor');
bootEditor(document.querySelector('#editor'));
```

읽으러 온 사람에게는 예전과 똑같이 정적 HTML만 보인다.

## 발행 과정은 건드리지 않았다

가장 신경 쓴 것은 발행 과정을 그대로 두는 일이었다. 글의 점검과 연결성 제안, 커밋까지 이미 잘 돌아가는 구조를, 에디터 하나를 바꾼다고 수정할 수는 없었다.

그래서 건드린 곳은 textarea 하나뿐이다. 에디터에서 무엇을 하든 그 결과를 마크다운으로 바꾸어서 화면 뒤 `#fm-body` textarea로 보낸다. 발행도, 점검 과정도, 글 간의 연결 제안도 예전처럼 이 textarea 값만 읽는다. 에디터는 교체했지만 발행 쪽에서 바라보는 대상은 그대로 두었다.

코드로는 한 줄만 추가하면 된다. 에디터의 내용이 바뀔 때마다 직렬화(화면에 보이는 내용을 글자 데이터로 바꾸는 일)해서 textarea로 전달하도록 했다. 이 한 줄에서 `getMarkdown()`으로 화면을 마크다운 문자열로 되돌리고, `normalizeMarkdown()`으로 그 결과를 다듬은 다음, `onChange`로 textarea에 값을 써 넣는다.

```ts src/scripts/milkdown-editor.ts
// 에디터가 바뀔 때마다 마크다운으로 직렬화해 textarea로 보낸다
opts.onChange(normalizeMarkdown(editor.action(getMarkdown())));
```

이렇게 연결한 흐름을 그리면 아래와 같다.

```mermaid
flowchart LR
    A[위지윅 방식으로 편집] --> B[마크다운으로 변환]
    B --> C[숨겨진 textarea]
    C --> D[점검/연결 제안]
    D --> E[커밋 & 배포]
```

덕분에 발행 쪽은 이 코드의 존재조차 모르고, 에디터가 바뀐 줄도 모른다. 어려운 일은 그 변환 과정에서 일어났다.

## 비표준 문법을 지키는 일

까다로운 것은 따로 있었다. 위지윅은 화면의 내용을 다시 마크다운으로 풀어내는데, 이때 Injoy만의 비표준 문법이 쉽게 깨졌다. 문법마다 지키는 방법은 아래 표와 같다.

| 문법              | 지키는 방법                             |
| --------------- | ---------------------------------- |
| 수식 `$...$`      | 전용 수식 플러그인이 노드(에디터가 다루는 내용 조각)로 보존 |
| 다이어그램/각주/이모지    | 표준 규칙으로 그대로 적용                     |
| 콜아웃 `> [!NOTE]` | 직렬화할 때 끼어든 이스케이프를 되돌려 복원           |
| 위키 링크 `[[슬러그]]`  | 위와 같은 방식으로 복원                      |

콜아웃과 위키 링크는 마크다운으로 풀 때 대괄호 앞에 백슬래시가 끼어드는 문제가 있었다. 이런 끼어듦을 이스케이프라고 한다. 이를 되돌리는 보정을 추가하되, 코드 블록과 인라인 코드 안에서는 절대 손대지 않도록 막아두었다.

이 보정은 마크다운을 한 줄씩 읽으면서 진행한다. 이때 코드 펜스(코드 블록을 여닫는 표시 줄)를 만나면 `fence` 변수에 그 표시를 기억해 두었다가, 짝이 되는 닫는 표시가 나올 때까지 그 안의 모든 줄을 손대지 않고 그대로 내보낸다. 코드 안에 적어둔 `[[대괄호]]`나 정규식(문자열에서 패턴을 찾는 규칙) 예시가 보정 대상에서 제외되는 것도 이 때문이다. 위키 링크와 콜아웃 마커는 코드 바깥의 줄에서만 되살린다.

```ts src/scripts/milkdown-editor.ts
export function normalizeMarkdown(md: string): string {
  const lines = md.split('\n');
  let fence: string | null = null;
  return lines
    .map((line) => {
      const fenceTok = line.match(/^\s*(`{3,}|~{3,})/)?.[1];
      if (fence) {
        // 코드펜스 안, 닫는 펜스를 만나기 전까지 전부 그대로
        if (fenceTok && fenceTok[0] === fence[0] && fenceTok.length >= fence.length) fence = null;
        return line; // [!code highlight]
      }
      if (fenceTok) { fence = fenceTok; return line; } // [!code highlight]
      // 코드 밖 줄에서만 보정하도록 한다
      return restoreWikiOutsideInlineCode(line).replace(CALLOUT_LINE, '$1[$2]');
    })
    .join('\n');
}
```

코드 펜스로 감싼 코드는 이렇게 지켰지만, 인라인 코드(문장 속에 백틱으로 감싼 짧은 코드)는 한 줄 안에 섞여 들어오기 때문에 방식이 달랐다. 한 줄을 인라인 코드(백틱) 기준으로 조각내면 코드가 아닌 부분과 코드인 부분이 번갈아 나온다. 이 중 코드가 아닌 부분에서만 `\[\[`를 `[[`로 되돌리면, 코드 안에 일부러 쓴 백슬래시 예시는 그대로 남는다.

```ts
function restoreWikiOutsideInlineCode(text: string): string {
  return text
    .split(/(`+[^`]*`+)/) // 괄호가 있어 구분자(인라인 코드)도 배열에 남는다
    .map((seg, i) => (i % 2 === 1 ? seg : seg.replace(/\\\[\\\[/g, '[[').replace(/\\\]\\\]/g, ']]')))
    .join('');
}
```

이런 예외를 두지 않으면 어떻게 되는지는 실제로 겪었다.

> [!WARNING]
> 이 예외를 빠뜨리면 코드 안에 쓴 대괄호까지 보정 대상이 되어 **멀쩡한 코드가 망가진다.** 처음엔 실제로 그렇게 짰다가 코드가 손상되는 걸 발견하고 급히 되돌렸다.

## 빌드가 통과해도 안심할 수 없는 코드

에디터를 새로 만들면 데이터가 깨지기 쉽기 때문에, 본 코드에 합치기 전에 적대적인 리뷰 에이전트를 한 번 실행했다(Claude Code의 ultracode 모드). 여러 에이전트가 흠을 찾는 방식인데, 이 리뷰에서 눈으로는 놓칠 뻔한 데이터 손상 문제가 두 개나 발견되었다. 그중 하나가 방금 설명한 코드 안 대괄호 보정 문제였다.

빌드는 멀쩡히 통과하는데 배포하고 나서야 결과물이 틀어지는 부류의 버그였다[^1]. 직렬화처럼 입력과 출력이 같아야 하는 코드일수록, <u>빌드가 통과했다는 안도감이 오히려 위험하다</u>는 것을 알게 되었다.

[^1]: 그래서 이런 코드는 사람 한 명의 눈보다, 서로 물고 늘어지는 여러 시선이 낫다고 느끼게 되었다.

## 남은 것

Notion과 같은 슬래시(`/`) 메뉴는 아직 없어서, 지금은 모바일에서도 안전한 툴바로 대신하고 있다. 콜아웃 맨 앞에서 글자를 지우면 숨은 마커가 같이 지워지고, 그 때문에 발행할 때 평범한 인용으로 바뀌는 자잘한 문제도 남아 있다. 이 두 가지는 천천히 고쳐 가려고 한다.

글을 쓰는 일은 확실히 나아졌다. 각 요소가 실제로 어떻게 보이는지는 [[markdown-styleguide|문법을 모아 둔 글]]에 정리해 두었고, 글을 올리는 전체 방법은 [[how-to-write|글을 올리는 방법을 적은 글]]에 적어두었다. 이 블로그가 하려는 일은 결국 글쓰기를 가로막는 마찰을 줄이는 것이고, 이번에는 글을 작성하는 화면 차례였다. 🌱
