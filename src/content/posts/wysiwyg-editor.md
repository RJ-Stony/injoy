이 블로그는 마크다운 파일 하나만 추가하면 그게 곧 발행이 된다는 단순한 구조로 되어있다. 그런데 정작 글을 쓰는 화면은 그 단순함과 거리가 멀었다. 왼쪽 칸에 `##`와 `>`와 백틱을 직접 입력하고, 미리보기로 결과를 확인하는 식이었다. 익숙해지면 빠르지만 문법을 머릿속에 담고 있어야 했다. 노션이나 토스 에디터의 매끄러움과는 분명히 달랐다.

그래서 이번에 글쓰기 화면을 통째로 바꿨다. 마크다운 기호를 직접 치는 대신, 보이는 그대로 편집하는 위지윅(WYSIWYG) 방식으로.

## 보이는 대로 쓰기

새 에디터는 Milkdown으로 만들었다. ProseMirror 위에 remark를 얹은 구조라 화면에서는 제목이 제목으로 인용이 인용으로 보이지만 속으로는 여전히 마크다운을 다룬다. `**굵게**`라고 치면 별표가 사라지면서 글자가 굵어진다. 노션에서 쓰던 그 감각 그대로다.

> [!NOTE]
> Milkdown은 완성된 에디터라기보다 에디터를 조립하는 부품에 가깝다. 표, 코드블록, 수식 같은 기능을 플러그인으로 하나씩 끼워 넣어 Injoy에 맞는 편집기를 짰다.

이 무거운 에디터는 방문자에게 전혀 실리지 않는다. 글쓰기 화면(`/write`)에서만 동적 import로 불러오기 때문이다.

```ts
// 글쓰기 화면이 실제로 열렸을 때만 로드된다
const { bootEditor } = await import('../scripts/milkdown-editor');
bootEditor(document.querySelector('#editor'));
```

읽으러 온 사람은 예전과 똑같이 정적 HTML만 보인다.

## 발행 과정은 건드리지 않았다

가장 신경 쓴 부분은 따로 있다. 발행 흐름을 한 줄도 고치고 싶지 않았다. 점검과 연결 제안, 커밋까지 이미 잘 돌아가는 길을 편집기를 바꾼다고 흔들 수는 없었다.

답은 숨은 textarea였다. 에디터에서 무엇을 하든 그 결과를 마크다운으로 바꿔 화면 뒤편의 `#fm-body` textarea로 흘려보낸다. 발행도 점검도 연결 제안도 예전처럼 이 textarea 값만 읽는다. 편집기는 갈아 끼웠지만 발행이 바라보는 진실은 그대로 둔 셈이다.

```mermaid
flowchart LR
    A[위지윅 편집] --> B[마크다운으로 변환]
    B --> C[숨은 textarea]
    C --> D[점검·연결 제안]
    D --> E[커밋 & 배포]
```

덕분에 발행 코드는 제 밑에서 에디터가 통째로 바뀐 줄도 모른다.

## 비표준 문법을 지키는 일

진짜 까다로운 건 따로 있었다. 위지윅은 화면의 내용을 다시 마크다운으로 풀어내는데, 이 과정에서 Injoy만의 비표준 문법이 쉽게 깨졌다.

| 문법              | 지키는 방법                   |
| --------------- | ------------------------ |
| 수식 `$...$`      | 전용 수식 플러그인이 노드로 보존       |
| 다이어그램·각주·이모지    | 표준 규칙으로 그대로 왕복           |
| 콜아웃 `> [!NOTE]` | 직렬화할 때 끼어든 이스케이프를 되돌려 복원 |
| 위키링크 `[[슬러그]]`  | 위와 같은 방식으로 복원            |

콜아웃과 위키링크는 마크다운으로 풀 때 대괄호 앞에 백슬래시가 끼어드는 문제가 있었다. 이걸 되돌리는 보정을 넣되 코드블록과 인라인 코드 안에서는 절대 손대지 않도록 막았다.

> [!WARNING]
> 이 예외를 빠뜨리면 코드 안에 쓴 대괄호까지 보정 대상이 되어 멀쩡한 코드가 망가진다. 처음엔 실제로 그렇게 짰다가 코드가 손상되는 걸 발견하고 급히 막았다.

## 빌드가 통과한다고 안심할 수 없는 코드

새 에디터는 데이터가 깨지기 쉬운 자리라 본 코드에 합치기 전에 적대적 리뷰를 한 번 돌렸다. 여러 에이전트가 작정하고 흠을 찾는 방식인데, 여기서 눈으로는 놓칠 뻔한 데이터 손상 두 건이 걸렸다. 그중 하나가 방금 말한 코드 안 대괄호 보정 문제였다.

빌드는 멀쩡히 통과하는데 발행하고 나서야 결과물이 틀어지는, 조용한 부류의 버그였다[^1]. 직렬화처럼 입력과 출력이 같아야 하는 코드일수록, 통과하는 빌드가 주는 안도감이 오히려 위험하다.

[^1]: 그래서 이런 코드는 사람 한 명의 눈보다, 서로 물고 늘어지는 여러 시선이 낫다고 느꼈다.

## 남은 것

슬래시(`/`) 메뉴는 아직 없다. 지금은 모바일에서도 안전한 삽입 툴바로 대신하고 있다. 콜아웃 맨 앞에서 글자를 지우면 숨은 마커가 다쳐 발행할 때 평범한 인용으로 강등되는 자잘한 문제도 남아 있다. 천천히 고쳐 갈 일이다.

쓰는 맛은 확실히 나아졌다. 각 요소가 실제로 어떻게 보이는지는 [[markdown-styleguide]]에 모아 두었고, 글을 올리는 전체 흐름은 [[how-to-write]]에 적어 두었다. 결국 글쓰기를 가로막는 마찰을 줄이는 게 이 블로그의 거의 전부고, 이번엔 쓰는 화면 차례였을 뿐이다. 🌱
